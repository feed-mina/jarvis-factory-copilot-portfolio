# Javis 위젯 예상안 자동 피드백

목표: 제공된 보고서에 근거해 MIMO 상품 카드와 KMovement 장소 카드를 비교하고, MIMO 예상안을 작성·검토·보완한 뒤 사용자 검토에서 멈춘다.

## 실행 범위

- 사용자가 승인한 범위는 예상안 작성·검토·보완이다. 위젯 구현, 배포, 고객 연락은 포함하지 않는다.
- `widget_planning.py`는 메일 API와 분리된 CLI 작업이다. Javis 웹의 실행 버튼, Kanban 접수, 상시 감시 또는 새 보고서 자동 감지와 연결됐다는 뜻은 아니다.
- Javis 제어기가 A01 컨테이너의 기존 모델로 다음 작업을 판단하고 독립 검토한다. 작성은 A03 컨테이너의 기존 모델을 호출한다.
- 기존 `role_runner.py`를 재사용하며 모델의 도구는 비활성이다. 보고서의 내용을 명령으로 실행하지 않는다. 파일 출력은 제어기가 HTML escaping을 거쳐 수행한다.
- 작성은 최대 3회(최초 1회 + 보완 2회). 통과하면 `awaiting_user_review`, 보완 한도에 도달하면 `revision_limit`. 모델 오류나 스키마 오류는 `failed`로 기록한다.
- 모델 검토 통과는 실제 앱·브라우저 검증이나 고객 승인과 다르다.

## 연결 흐름

보고서 묶음 → A01 판단 → A03 작성 → A01 검토 → 부족하면 피드백을 포함해 A03 재작성 → 사용자 검토 대기.

입력 JSON에는 `goal`과 `sources` 배열을 둔다. 각 source는 `id`, `path`, `sha256`, `text`를 가진다. SHA는 제공자가 실제 입력 파일에서 계산하고, 추출 텍스트는 읽은 범위를 명시한다. 파일의 실제 앱 상태를 검증했다는 의미가 아니다.

실행 위치는 Javis 서버의 독립 디렉터리다. 같은 디렉터리에 기존 `role_runner.py`를 함께 둔다.

```sh
python3 -m unittest test_widget_planning -v
python3 widget_planning.py bundle.json runs/<고유 실행 ID>
```

`state.json`에는 읽은 자료 경로·해시, 판단·작성·검토 이벤트, 모델 정보, 각 회차의 예상안과 검토 결과가 남는다. `report.html`은 실제 스크린샷과 구분한 GUI 모형을 포함한다.

같은 출력 폴더에 상태가 있으면 모델을 다시 호출하지 않는다. 중단·실패한 실행을 자동으로 재전송하지 않는다. 원인을 확인한 후 새 고유 실행 ID로 재실행한다. 동시 실행은 배타 파일 잠금으로 막는다. 비정상 종료 후 남은 잠금은 프로세스 종료를 확인한 후 운영자가 처리한다.

## 다음 통합 지점

웹 연결 시 인증된 별도 작업 API에 이 실행기를 붙이고 작업 ID·상태·결과를 표시해야 한다. 기존 메일 작업 ID나 메일 DB에 위젯 계획을 저장하지 않는다. 시작 요청에는 입력 digest 기반 중복 방지, 상태 조회에는 소유권 검사를 적용한다. 임의 파일 경로나 프롬프트를 실행 권한으로 받지 않는다.

현재 모듈은 이 첫 제어 루프를 실제 실행하기 위한 것이며, 16개 저장소를 순차로 자동 구현하는 기능은 아니다.
